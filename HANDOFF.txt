A. PROJECT IDENTITY
================================================================================
1. Purpose & Commercial Use Case
   TijaraGuard is a self-hosted and cloud-deployable commercial customer-support
   and sales-assistance platform designed for Arabic (Gulf, Egyptian, Levantine,
   Modern Standard Arabic) and English retail/merchant operations. It sits
   between inbound customer messaging channels (WhatsApp Business Cloud API,
   Telegram Bot API, Chatwoot, Generic Signed Webhook/REST), external or local
   AI drafting models (OpenAI-compatible providers, Anthropic Claude, Google
   Gemini, optional Ollama), human supervisors, and outbound delivery,
   enforcing four mandatory safety gates so raw customer PII never leaks and
   AI hallucinations never become unauthorized commercial promises.

2. Current Architecture
   - Zero external PyPI runtime dependencies (`dependencies = []` in
     `pyproject.toml`, Python >=3.11 stdlib + SQLite WAL).
   - Four sequential gates orchestrated by `TijaraGuardPipeline`:
     * Gate 1 (Privacy / BayanGate): Redacts regional/MENA PII and replaces raw
       contact identifiers with HMAC-SHA256 `contact_ref` handles *before* AI
       model calls, SQLite writes, logs, or exceptions.
     * Gate 2 (Commercial Truth / CatalogCopilot): Parses Arabic dialect and
       English inquiries, resolves catalog SKUs, validates documented consent,
       and deterministically verifies prices, stock, discounts, warranty terms,
       and claims (treating AI outputs as untrusted drafts).
     * Gate 3 (Human Approval / ApprovalLedger): Defaults to Shadow Mode
       (`SIMULATED_NO_SEND`), binds single-use HMAC-SHA256 approval leases
       atomically to `(draft_id, payload_sha256, lease_id)`, supports
       edit/re-verify/reject/escalate, and records an append-only SHA-256
       hash-chained `audit_events` log protected by SQLite immutability triggers.
     * Gate 4 (Reliable Delivery / MessageShield): Uses durable outbox tracking,
       deterministic idempotency keys, conservative `UNKNOWN_DELIVERY` handling,
       read-only receipt reconciliation without blind replay, and isolated
       `EphemeralRouteStore` (`routes.sqlite3`) target resolution.

2. SQLite Persistence Schema (Schema v2 — `ledger.sqlite3`)
   - `schema_migrations(version, applied_at, description)`
   - `drafts`: Stores ONLY redacted inquiries, opaque HMAC `contact_ref`, hashed
     `conversation_id`, commercial verification reports, canonical `payload_sha256`,
     workflow `state`, delivery key/receipt, `ai_provider`/`ai_model`/`ai_metadata_json`,
     sanitized `channel_metadata_json`, `escalation_reason`, `retention_expires_at`,
     and `tenant_id`. Never stores raw phone numbers or external chat IDs.
   - `approvals`: Single-use HMAC-SHA256 approval leases bound to `(draft_id,
     payload_sha256, lease_id)` with unique partial index `idx_one_active_approval`.
   - `audit_events`: Append-only hash-chained event table (`seq`, `prev_hash`,
     `event_hash`) protected by `audit_events_no_update` and `audit_events_no_delete`
     SQLite triggers.
   - `channel_events`: Channel webhook/update idempotency & replay deduplication
     with hashed `external_event_id`.
   - `provider_usage`: Per-attempt AI provider latency, token counts, cost, status,
     and failure classification linked to `draft_id` and `tenant_id`.
   - Safe `v1 -> v2` migration adds v2 columns/tables/indexes in a transaction, runs
     `PRAGMA foreign_key_check`, and preserves historical `audit_events` & triggers.
   - Separate `routes.sqlite3` (`EphemeralRouteStore`): Stores TTL-expiring delivery
     routing targets keyed by `(tenant_id, channel, contact_ref, external_conversation_id)`
     with automatic upgrade from legacy 3-column primary keys.
